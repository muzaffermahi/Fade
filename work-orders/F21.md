F21 storage contract (implemented; external release qualification remains separate):

- Preserve explicit v1/v2/v3/v4 schemas for legacy reads and exclusive byte backups before migration. Introduce validated v5 runtime/reference records and a separately validated persisted index/journal format. Existing project/session IDs, revision guards, check authority, exact criteria and provenance remain intact. Large image/base64 strings, human/model text, historical intent snapshots and raw operation JSON are content-addressed by SHA-256 under guarded .fade payload paths. References carry exact encoded byte size and encoding; reads verify hash/size before decoding. Legacy payload strings are preserved byte for byte, including data that fails the new send limits/signatures.
- Durable acceptance writes all referenced payloads/archival records before fsync of the authoritative journal. Archive byte boundaries belong to the committed index, so orphan records from a failed append cannot become accepted history. Incremental validated journal changes avoid rewriting an unchanged index on every status update; durable checkpoints bound normal replay. Crash recovery remains paused and never replays uncertain work.
- Runtime windows retain recent records and all necessary in-flight input, immutable briefs, dependency/check evidence and unresolved failures. Cold provenance moves to append-only archives with validated paging/identity lookup; terminal/model projections never hydrate every raw result or attachment. Check latest results remain available and older manual command IDs remain idempotent through archived lookup. Explicit archive inspections/searches may scan disk with bounded page memory. Limits and overflow handling must be tested rather than silently dropping unresolved authority/evidence. The existing 250-receipt test will assert retained archive provenance instead of requiring all receipts in the hot array.
- New sends validate canonical base64 PNG/JPEG/WebP signatures, at most 20 images, 15*1024*1024 decoded bytes each and 30*1024*1024 aggregate; supported model capability is checked where known. Exactly 20,000 characters may be sent; larger drafts remain editable. Draft-only marker identity is stable and removal/deletion removes the corresponding pending image. A visible per-role tray and local attachment-management picker provide removal; the picker uses public Pi TUI APIs and a documented local Ctrl+Alt+I binding. It does not authorize effects or invoke a provider.
- Draft metadata is coalesced on a fixed deadline no later than 150ms after the first unsaved edit, without postponing the deadline indefinitely. Large payloads are deduplicated outside metadata rewrites. Submission, role/mode switch, native handoff, session change and shutdown synchronously flush the corresponding pending draft; failed best-effort saves remain visible with the in-memory draft retained. Accepted receipts are never batched.
- Intermediate tool display updates may coalesce for at most 150ms; start/end and final verification remain immediate and durable. Final output is retained losslessly; queued display output is not described as durable until flushed. Final split performance evidence must include 1,000 receipts, substantial tool history, attachments and concurrent output with bounded arrays/cache sizes, RSS and disk measurements, current-screen checks, warm startup <=2s, echo p95<50ms and received activity/completion <=250ms. Provider/physical terminal/IME/platform qualification stays separate.
